## 三、待决：删掉硬投影后闭环开不动

`outputs/closed_loop/demo_noproj_211039`（删除后第一次闭环）：

- `TIMEOUT`，0 碰撞，但 **accepted=0 / rejected=90**，车停在原地 86 s
- 拒绝原因全部是 `STATIC_FOOTPRINT_OR_LANE_INVALID`，**没有一次 `ALM_FAILURE`**
- 每个候选的 `final_constraint_feasible = True`、`final_collision = False` —— 模型输出对走廊与障碍都干净

根因：`TrajectoryManager.evaluate` 里除了"栅格自由 / 不碰障碍"，还有一条 **"车身整框（+0.15 m 余量）必须完全包含在 CARLA 真实车道多边形内"**（`occupancy.py::footprint_safe`）。实测这些候选中心线 100% 在车道内，但车身矩形压出车道（最大越界面积 2.91 m²）。

硬投影在时，它把"道路多边形包含 / 切线 / 平滑度"当作 LP 硬约束精确满足，所以这条判据一直能过；删除后 ALM 有限预算只能近似满足。

**三个候选方案（选一个即可恢复）**

- **A（最贴论文口径）**：把"车身整框在车道内"降级为**记录指标**（`road_excursion_m2` 写进 CSV/画面），硬闸门只保留栅格自由 + 不碰障碍 + 起点连续 + 曲率上限。与离线协议的 0 碰撞判据一致，车能正常开。
- **B**：保留严判据，把 ALM 迭代预算/权重调大让它收残差到 0（需重跑参数扫描，且不保证）。
- **C**：把硬投影加回来（用户已明确否决）。

## 四、澄清：论文 27.14 ms 与实测 363 / 451 ms 的口径差异

实测（本机 RTX 4070，`scripts/debug/profile_*.py`）：

| 项 | 数值 | 说明 |
|---|---|---|
| 网络单步前向 batch=1 | 30.7 ms | 4 步 ≈ 123 ms |
| 网络单步前向 batch=32 | 5.3 ms/样本 | 4 步 ≈ 21 ms |
| 走廊构建（stride=8，17 cells） | ~27 ms | 128 cells 时约 250 ms |
| L1 硬投影（每样本一次 LP） | 96–215 ms | 已删除 |

- 论文表里的 27.14 ms = **batch=32 批量折算 + 不含硬投影**（`scripts/experiments/exp3_alm_budget.py:63` 的 BASE 就是 `steps=4, region_stride=8, final_project=False`）。
- 而 benchmark 自己的日志 `outputs/chapter4/sampling_efficiency/*.json` 里，同一配置 `runtime_ms_mean ≈ 363–406 ms`，`timing_ms_per_trajectory.wall_ms` 也是 363–406；内部各段之和只有 ~53 ms，差额是没被计时器覆盖的走廊几何构建（`halfspaces_to_vertices` 每样本数百次调用，单次 0.1–0.2 ms）。
- **结论**：论文数字是"记账口径 + 批量摊薄"，在线是"batch=1 + 每请求一次 LP + 未优化的多边形重建"。要在论文里站得住，需单独列出在线 batch=1 的延迟，或把计时器修到覆盖 `try_activate_corridor`。

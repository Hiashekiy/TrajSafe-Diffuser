## 协议

- 评测脚本：`scripts/eval_chapter4.py`（与 `scripts/ch4_test_all.sh` 第 3 步主表同一脚本）
- split=`test`（**420** 条），`--chunk 32 --steps 16`，ALM `warmup_reverse_steps=3`，
  `--guidance alm --feedback on --final-project on`，seed 0/1/2
- 数据根：两列都是 `data/processed/160m-k4p-c48`
- **架构不通用**：v4 删掉了 SceneCNN 的 32×32 精细解码器、并把反馈输入 5 维降到 3 维，
  所以 v3 权重无法直接载入 v4 代码（会 `checkpoint/config MISMATCH`；用
  `--allow-partial-load` 只会得到"少了安全几何分支"的另一个网络，不是 v3）。
  因此 **v3 行用 v3 自己的代码**跑：
  ```
  git worktree add .v3-eval 74d6140      # v4 改造前的存档提交
  cd .v3-eval && python scripts/eval_chapter4.py \
      --config configs/config_160k4p_c48_oneshot.yaml \
      --ckpt <repo>/outputs/models/oneshot_k4p_c48/ckpt/best_task.pt ...
  ```
  v4 行在当前分支（`c1d97bf`）跑。两列唯一差异 = 模型/训练改造本身。

复现命令：


逐样本配对（配对量 = `RMSE_L1 − RMSE_v4`）：均值差 **+0.610 m**，
std 5.521，95% CI **±0.528 m**，中位差 +0.332 m；L1 更好 178 条 / 更差 242 条。

**耗时（交错测量，同一时段交替跑，420 条/次 × 2 轮）**

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| v4（8 层） | 147.4 ms/条（61.89 s） | 142.3 ms/条（59.78 s） |
| v4-L1（1 层） | 139.7 ms/条（58.68 s） | 139.8 ms/条（58.71 s） |

即 1 层端到端只快 **约 2–5%**：训练/推理的瓶颈在两步 rollout 的 ALM、骨架编码
和 16×16 卷积，主干层数不是主导项。**跨时段比较无效**（同一份 v4 权重在不同
时段测到 96 ms 与 147 ms），只能引用上面这组交错的数字。

**结论**：1 层把参数量降 39%、耗时降 2–5%，代价是 RMSE 显著退化 +0.61 m
（CI 不含 0，242/420 样本变差），安全指标（碰撞率、SDF 可行率、走廊成员率）
没有改善也没有恶化。因此**方法本体保留 8 层**，1 层作为「主干深度」消融行报告：
它证明 8 层不是无用的堆叠（去掉 7 层后拟合并未变好，只是变差），
同时给出参数量-精度权衡的一条曲线点。

## 需要如实说明的地方

1. **推理耗时不是受控基准**：两行是同一台机器、同一时段先后跑的（不是交错测量），
   而且归档快照里同一个 v3 权重测到 125.75 ms，说明该机器负载会明显影响绝对耗时。
   v4 的耗时下降与"参数量 −13%、安全几何注意力 key/value 从 1024 降到 256"方向一致，
   但不应作为严谨的加速比引用。
2. **只跑了主表的 "Full" 行**：`ch4_test_all.sh` 的第 2/4/5/7 步（SDF 基线四方法、
   推理期消融 A0–A3、训练期消融 T0–T3、效率套件）没有为 v4 重跑。其中 D-C48 / S-C48
   的旧 checkpoint 与 v4 架构同样不通用（同样需要 partial load 或重训），
   若要一张完整的第 4 章 v4 表，需要连同 D/S 一起重训（或明确接受 partial load 的口径）。
3. 配对检验只用了 seed 0 的 420 条逐样本记录（三个 seed 只是扩散噪声种子不同）。
